# Bitwarden.Server.Sdk.Service

## About

The package a Bitwarden .NET service references. A service derives from `Service`, gives it an
identifier and a title, and maps its endpoints as minimal APIs. The base class owns the rest of
startup: the order of dependency registration and of middleware is security-relevant, so it is fixed
in `Service.Build()` rather than rediscovered by each service.

Every service gets, in a fixed order:

- authentication of every request by default, with token audiences always checked;
- authorization by scope and by the organization, user and provider a request concerns;
- the standard request and response documents, binding, validation and error documents;
- querying (filters, sorting, offset and cursor paging, sparse fieldsets) and bulk operations;
- an OpenAPI document and a documentation UI;
- traces, metrics and logs over OTLP;
- per-address request limits, CORS for named browser origins, and health probes;
- feature flags, and for a product service a `GET /api/v1/config` resource;
- idempotency keys: a write another service sends with an `Idempotency-Key` is done at most once (below).

Most of that lives in smaller packages, which this one references and registers in order, so a
service references this package alone:

This package keeps the `Service` base class and its startup order, self-hosting, the system endpoints,
telemetry and health publishing, the general OpenAPI setup and documentation UI, the config resource
and its feature-flag context, serving internal TLS, finishing writes whose client left, the guard on
operations whose writes span services, and `GetOrResolveOnceAsync`.

Bitwarden services are zero knowledge: they store and synchronize Vault Data only as Protected Data,
encrypted on the client. Nothing in this package decrypts an encrypted value. A resource declares
an encrypted member with `[Encrypted]` from Bitwarden.Server.Sdk.Data.Abstractions, which checks its
length and, with `WellFormed = true`, that it is shaped like an encrypted string.

## Installing

```bash
dotnet add package Bitwarden.Server.Sdk.Service
```

## Bitwarden.Server.Sdk and `UseBitwardenSdk()`

The `Bitwarden.Server.Sdk` MSBuild SDK offers `UseBitwardenSdk()`, which layers in self-hosted
settings, sets up OpenTelemetry and, depending on what the project turns on, adds authentication and
feature flags. A service built on `Service` gets all of that from `Service`, so it does not call
`UseBitwardenSdk()` as well: the two would register the bearer scheme twice, which fails with
"Scheme already exists: Bearer".

The settings both read mean the same thing in both:

- `globalSettings:selfHosted` marks a self-hosted install and layers in
  `appsettings.SelfHosted.json` after `appsettings.{Environment}.json`;
- `OpenTelemetry:Enabled`, `OpenTelemetry:Tracing:Enabled` and `OpenTelemetry:Metrics:Enabled` turn
  the exporters on or off, on by default in the cloud and off when self-hosted
  (`OpenTelemetry:Logging:Enabled` is read by `Service` only);
- the `DD_ENV` environment variable is added to the telemetry resource as `env`.

## Idempotency keys

[Bitwarden.Server.Sdk.Idempotency](https://github.com/bitwarden/dotnet-extensions/blob/main/extensions/Bitwarden.Server.Sdk.Idempotency/src/README.md) does this, and
`Service` turns it on for every service. A write (any method but `GET`, `HEAD`, `OPTIONS` and `TRACE`) from another service's credential
(`internal.{name}`) that carries an `Idempotency-Key` header, as every write the client package sends does, is done
at most once per caller and key (IETF draft "The Idempotency-Key HTTP Header Field"):

- the first holds the key while it runs, and its answer, when it completed (a status below `500` written by the
  operation), is kept for `Idempotency:Retention`;
- a repeat with the same method, path, query and body is answered with that answer, marked
  `Idempotency-Replayed: true`, without running again;
- a repeat with a different request is refused `422`; one while the first still runs, `409` with `Retry-After`,
  which the client package waits for within its deadline;
- a write that failed (a `5xx`, or an exception) keeps nothing, so its repeat runs again.

A browser's write is untouched, whatever it carries, so every client-facing operation behaves as it always has. An
operation that must run every time opts out with `[IgnoreIdempotencyKey]`; the client package retries a keyed write
after a failed connection, so such an operation must be safe to receive twice. A `POST` that only reads (a check, a
look-up, a validation, a preview) opts out the same way, so a caller's operation run again is answered from the state
now, never from an older record. A write asked only to be
checked (`validateOnly=true` in the query) changes nothing, so it is never recorded either.

Records live in Redis (`Idempotency:Redis:Configuration`) under the service's own prefix, so every
instance shares them, when the service also persists a data protection key ring every instance reads;
otherwise in the process. What is kept is only what the operation already answered the caller (Protected Data or
metadata, never plaintext Vault Data, which no service holds), sealed with the service's data protection keys, since
the services that call this one may read its prefix of a shared Redis. While the store is unavailable, a write runs as it would without
a key; a record this instance can't open is refused as still running, never run past.

## Getting started

Derive from `Service`, give it an identifier and a title, and map your endpoints, each resource's
handlers in a class of their own:

```csharp
using Bitwarden.Server.Sdk.Errors;
using Bitwarden.Server.Sdk.Resources;
using Bitwarden.Server.Sdk.Service;
using static Bitwarden.Server.Sdk.Resources.StandardResponses;

new WidgetService(args).Run();

internal sealed class WidgetService(string[] args) : Service("widget-service", "Widget Service", args)
{
    protected override void ConfigureServices(IServiceCollection services)
    {
        services.AddOpenApi();
        services.AddSingleton<IWidgetStore, WidgetStore>();
    }

    protected override void MapEndpoints(IEndpointRouteBuilder endpoints) =>
        WidgetsEndpoints.Map(endpoints);
}

[ApiTag(Description = "Widgets, which a person keeps.")]
public static class WidgetsEndpoints
{
    public static void Map(IEndpointRouteBuilder endpoints) =>
        endpoints.MapGroup("api/v1/widgets").WithStandards().MapGet("{id}", GetWidget);

    /// <summary>
    /// Get a widget
    /// </summary>
    [StandardReadOne]
    public static async Task<ResourceDocument<Widget>> GetWidget(
        string id, IWidgetStore store, CancellationToken cancellationToken) =>
        ReadOneResponse(await store.FindAsync(id, cancellationToken)
            ?? throw new NotFoundException("widget", id));
}
```

The project needs the request delegate generator and XML documentation turned on, as the README
shows.

The [README](https://github.com/bitwarden/dotnet-extensions/blob/main/extensions/Bitwarden.Server.Sdk.Service/README.md#getting-started)
walks through a complete first service: the project file, a resource, running it and calling it.
